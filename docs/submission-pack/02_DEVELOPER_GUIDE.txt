1. PROJECT OVERVIEW
================================================================================

Azure Bay is a full-stack hotel product:

  Public site  — discover rooms, book stays, dining (when in-house), messages
  Staff portal — run the house (desk, F&B, HK, inventory, reports, settings)
  API          — Express + MongoDB + JWT + Socket.IO

Business goals encoded in software:
  • Guests book against real inventory and date windows
  • Desk checks guests in/out, bills, messages
  • Managers own rates, media, menu, review publish
  • Admin owns staff accounts and hotel settings
  • Least privilege (see ACCESS_MATRIX)

4. LOCAL SETUP AND RUN
================================================================================

Prerequisites: Node.js LTS, MongoDB (local or Atlas URI in server/.env)

Server:
  cd server
  npm install
  # configure .env (see section 5)
  npm run dev
  → http://127.0.0.1:5000
  Health: GET /api/v1/health

Client:
  cd client
  npm install
  # VITE_API_URL or proxy to :5000 (see vite.config)
  npm run dev
  → http://127.0.0.1:5173

On API boot: connectDatabase → seedDatabase (idempotent if users exist) → listen.
Empty users collection triggers full demo seed.

  VITE_EMAILJS_TEMPLATE_ID=
  VITE_EMAILJS_PUBLIC_KEY=

Never commit secrets. Restart Vite after changing VITE_* keys.

================================================================================

Request path:
  UI → api() helper (Bearer access token per tab) → /api/v1/* → middleware
  → route handler → Mongoose → JSON

Live updates:
  Server publish("room" | reservation events | …) → Socket.IO → client useOpsPulse

Auth model:
  Multi-tab safe: prefer Authorization Bearer; cookies kept for compatibility.

7. AUTHENTICATION AND SESSIONS
================================================================================

Files: server/src/middleware/auth.js, routes/auth.js
       client/src/context/AuthContext.jsx, lib/session.js, lib/api.js

  • Sign access JWT (role in payload), refresh token hashed on User
  • requireAuth / requireRole(...roles)
  • Login rate limited
  • Guest register creates User(role=guest) + Guest profile
  • Signup OTP via EmailJS on client before register (when configured)

Role homes: client/src/lib/roles.js → /admin, /staff, /guest, …

================================================================================
8. ROLES AND ACCESS CONTROL
================================================================================

Roles: admin | manager | receptionist | housekeeping | maintenance | guest

Official matrix: docs/ACCESS_MATRIX.md

Summary for developers:
  Staff CRUD + password reset     → admin only
  Settings PATCH (tax, window, stayPolicies) → admin only
  Inventory / Media / Menu CRUD   → admin + manager
  Dining kitchen/tables status    → includes receptionist
  Feedback publish                → admin + manager
  HK task list for housekeeping role → unassigned + own only
  Guest dining / room care        → checked_in stay required

UI must hide unauthorized tabs; API must still enforce (never UI-only security).

12. CLIENT ARCHITECTURE
================================================================================

App.jsx routes: public layout + lazy PortalPage / RoleGate
api(path, { method, body }) attaches Bearer token from session
Design system components under components/ui
Portal monolith: pages/PortalPage.jsx hosts role sections (Inventory, Settings, …)
Domain boards extracted: DiningBoard, HouseKanban, BookingsTable, DeskMessagesPanel

State:
  AuthContext — user session
  Zustand searchStore — stay dates/guests persist (azure-bay-search)
  Catalog hook — loadRoomCatalog() API with static fallback if API down

23. DEPLOYMENT NOTES
================================================================================

  • Build client: npm run build → static host / CDN
  • API: Node process manager; set CLIENT_ORIGIN to production URL
  • MongoDB Atlas recommended for hosted demos
  • Secure JWT_SECRET; HTTPS in production; secure cookies if used
  • Configure EmailJS + Cloudinary for full feature parity

================================================================================
24. CONVENTIONS (DO NOT BREAK)
================================================================================

  • Prefer extending existing components over parallel design systems
  • Update docs/WORKLOG.md and domain docs when shipping features
  • Enforce RBAC on API even if UI hides controls
  • Do not replace working booking/availability logic casually
  • Room content: amenities on RoomType; policies Setting; reviews Feedback
  • Keep PortalPage changes localized; extract boards when growing
